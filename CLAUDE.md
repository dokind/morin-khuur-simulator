# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An open-source Electron desktop app (Windows first; macOS/Linux targets configured) that simulates the Mongolian **Morin Khuur** (horsehead fiddle). Four views mirror the mockups in `design_references/`: **Playground** (live playing: side-stop pads, tsatsal nodes, bow gesture pad, keyboard/MIDI), **Beat Maker** (4×4 technique pads + horse-gait step sequencer), **Song Tester** (plays `.mkhuur.json` songs and verifies they are physically playable) and **Studio** (4-track arrangement rendered to stems). A fifth, **Playlist**, compares our playback of popular morin khuur pieces with original recordings (links, A/B, blind test, automatic feature comparison, exportable feedback). `MORIN_KHUUR_FOUNDATION_SPEC.md` (techniques, song format, verification) and `MORIN_KHUUR_SIMULATOR_PLAN.md` (roadmap) are the product specs; the mockups are the UI blueprint.

## Commands

```bash
npm install                 # Electron 44 downloads its binary lazily; force it with: node node_modules/electron/install.js
npm run dev                 # Electron + Vite HMR
npm run dev:web             # renderer only, in a normal browser at http://localhost:5173 (no preload bridge; click once to unlock audio)
npm run typecheck           # tsc for tsconfig.node.json (main/preload/tests) and tsconfig.web.json (renderer)
npm run lint                # ESLint 10 flat config, includes React Compiler rules (react-hooks v7)
npm test                    # vitest (node environment)
npx vitest run src/renderer/src/core/notation/notation.test.ts -t "spec §5.2"   # single file / single test
npm run build               # typecheck + electron-vite build → out/
npm run dist:win            # build + electron-builder → dist/ (NSIS installer x64/arm64 + portable exe)
npm run icons               # regenerate build/icon.png + build/icon.ico from build/icon.svg
```

The bowed-string DSP is unit-tested in Node: `audio/worklets/bowed-string.test.ts` loads the worklet source with stubbed `AudioWorkletProcessor`/`registerProcessor`/`sampleRate`, runs it block by block and checks pitch with YIN. Everything else in `audio/` needs a browser: run `npm run dev:web` and use the dev-only `window.__mkhuur` handle (`engine`, `getPerformer`) or `import('/src/audio/offline.ts')` in the console — `measurePitch(event)` renders a note offline through the full chain and runs YIN on it. `window.__mkhuur.compareReference({ url, songId?, entryId?, start?, length?, referenceKind?, room? })` and `window.__mkhuur.analyzeUrl(url)` analyse a recording served by Vite (e.g. `/@fs/C:/…/references/conservatory-1999.mp3`) against our render and return the comparison rows as JSON. For long measurement scripts use the `renderer-measure` config in `.claude/launch.json` (port 5174, no HMR and no file watching — restart it after edits).

## Architecture

**Process split.** `src/main` creates the window, owns file dialogs (`file:save` / `file:open` IPC, sender-checked), grants only the `midi` permission and sets the autoplay policy so audio starts without a gesture. `src/preload` exposes `window.mkhuur` (contract in `src/shared/ipc.ts`, sandboxed/context-isolated). The renderer reaches it only through `src/renderer/src/platform.ts`, which falls back to browser download/upload when the bridge is absent (`dev:web`).

**`src/renderer/src/core/` is pure TypeScript** — no DOM, no Tone. Tests import it and are type-checked under `tsconfig.node.json` (no DOM lib), which keeps it pure; don't import audio/React code into it.
- `instrument.ts`: the two-string physical model — tunings (F3/B♭3 standard), stop positions from string physics (`stopFraction`), natural-harmonic nodes (`harmonicNode`, just-intonation partials), first-position fingering heuristic, string choice, keyboard layout.
- `techniques.ts`: the 16 techniques from spec §3 (ids are the song-format `technique` values), bow directions, and `SCREEN_DIRECTION` (see domain notes).
- `performance/`: the unwritten performance rules, as a pure **planner** — `planPerformance(song, report, bpm, { style, amount })` returns per-note ornaments (pentatonic scoops, graces, hammers, mordents, third-trills, falls, shift/trot slides), vibrato plans (lyrical / tsokhilt / bönjignökh / nogula; rate, depth, placement), bow profiles (swell, accent-release, abrupt), position ramps, shurankhai, automatic drone and framing strokes (om zee, long-song prelude). Styles in `presets.ts`: `as-written` (notation only), `khalkh-stage` (default; composed pieces: fixed rhythm, few ornaments), `urtiin-duu`, `tatlaga`, `bii-ikel`, `inner-mongolian`; `resolveStyle` picks one from `song.style` or the genre text. Deterministic (seeded per title and note). Every number is sourced or marked [ENG] in `presets.ts`.
- `analysis.ts`: audio feature extraction (pitch track, note segmentation robust to vibrato/scoops/reverb, vibrato rate/extent, harmonic balance, centroid, HNR, attack, tempo, transposition, melody match, LTAS…) and `compareFeatures(sim, ref, { referenceKind })` with tolerances as exported constants; `playlist.ts` is the hit list (rights, verified original-performance links, style hints).
- `notation/`: `.mkhuur.json` types → `parse.ts` (structure) → `verify.ts` (physics + phrasing rules) → `jianpu.ts` (numbered notation layout). Import from MIDI/MusicXML/.mxl with automatic string/finger/bow assignment is re-exported from `notation/index.ts`.
- `sequencer.ts` + `kit.ts` (Beat Maker model, grooves, pad metadata/MIDI map), `arrangement.ts` (Studio accompaniment generators), `pitch-detect.ts` (YIN), `wav.ts`, `midi.ts` (SMF writer).

**`src/renderer/src/audio/` (Tone.js 15).**
- `engine.ts`: lazy singleton graph (instruments → bus → `Room` → master → limiter → meters/recorder) plus shared `MorinKhuur` and `BeatKit` instances. Live input schedules at `Tone.immediate()`; transport content uses the 50 ms look-ahead.
- `bowed-voice.ts` wraps the `mkhuur-bowed-string` AudioWorklet (`worklets/bowed-string.worklet.js`): a bowed-string digital waveguide (friction junction, pitch-tracking loss filter, cubic Lagrange delays) with horsehair roughness and a **pitch lock**: once a cycle (at an upward zero crossing of the band-passed fundamental) it times the waveform's period over the last two cycles with a 5-lag difference function and trims the loop length — bow friction otherwise flattens short, high strings. The trim holds while the pitch moves (vibrato, slides) and is capped at 1.5% of the period. The worklet source is imported `?raw` and registered from a Blob URL by `dsp.ts`, per context, via the raw `audioWorklet.addModule` (Tone's own helper caches one module per context). Voices created before the module loads attach themselves when it does. `bowTimbre()` maps speed/pressure/bow point to model params: force rises with bow speed, and the contact point β takes only safe values (0.13 default, ~0.11 ponticello, `TASTO_BETA` 0.19 tasto) because bowing near a harmonic node (1/6–1/5, 1/3) makes the string lock onto that harmonic — the maps behind this are reproducible with the Node test harness.
- `body.ts`: the soundbox as a convolution with a generated modal impulse response — wooden top (modes at Bulanov's measured response maxima: 170, 280, 440, 780, 1200, 1800, 2300, 3500 Hz, tuned so the open F3 fundamental sits 1–2 dB below its next harmonics as he measured, with the fundamental dominating higher up) or traditional hide top (suukha khuur formants plus kamancheh membrane modes as a stand-in). Modes are absolutely scaled (peak = table dB) with alternating fixed phases, and run through a *native* `ConvolverNode` with `normalize = false`: `Tone.Convolver` assigns the buffer before its `normalize` option and rebuilds the node with the default on every buffer change, so it always normalises; `morin-khuur.ts` combines two voices (per-string hair profiles: male 130 hairs rougher/lossier), the soundbox, pizzicato/col legno/slap/knock/tsokhilgo (`strikes.ts`) and the whinny (`gestures.ts`).
- `song-player.ts` `songEvents(song, report, bpm, { style, amount })` turns the plan into timed `NoteEvent`s (frames have `order: -1` and never reach `onNote`); `reference.ts` decodes/stores reference recordings (IndexedDB), renders our version and runs the comparison; `offline.ts` `renderOffline` serialises every offline render in the app behind one lock (`whenOfflineIdle`), so views never build inside each other's context.
- `performer.ts` (Playground live-control rules), `beat-kit.ts` + `beat-sequencer.ts`, `studio.ts` (offline-rendered stems, mixer, take recorder), `accompaniment.ts` (tovshuur, khöömii).
- Every audio class builds its nodes against the *current* Tone context, so the same code renders live and inside `Tone.Offline` (`offline.ts`: `renderOffline` loads the worklet first, WAV export, `measurePitch`). Never cache nodes or buffers across contexts (caches are keyed by `rawContext`).

**State**: zustand stores in `state/` persisted to localStorage under `mkhuur.*`. **Songs**: `songs/*.mkhuur.json` are bundled via `import.meta.glob` in `songs.ts`; `library.test.ts` fails if any bundled song has a parse error or verification warning. View-level derived data goes through identity caches (`loadSong`, `memoLast`) rather than `useMemo`, to satisfy the React Compiler lint rules.

Mapping to the spec's planned `packages/`: audio-core → `audio/`, notation-engine → `core/notation/`, beat-maker → `core/sequencer.ts` + `audio/beat-*`, instrument-3d → `components/InstrumentView.tsx` (2D SVG; no 3D model yet).

## Domain rules and gotchas

- **Song format**: spec §5.2 plus optional extensions (`slur`, `velocity`, `articulations`, `glideTo`, `drone`, `key`, `source`) documented in `core/notation/types.ts`. Times use Tone.js `bars:beats:sixteenths` where a beat is a **quarter note** (a 6/8 bar has 3 beats); `tempoBpm` counts quarters.
- **Verification**: errors mean "physically impossible as written" (pitch off the string, one string sounding two pitches, harmonics not on a node, glide/drone out of range); warnings are pedagogy (fingering, bow alternation, vibrato on an open string). Harmonic expected frequencies use just ratios (open × n), not equal temperament. The spec's own §5.2 example fails (C4 is not a natural harmonic of B♭3) — a test pins this.
- **Acoustic test**: the Song Tester renders each distinct note offline and requires |error| < 5 cents (`PITCH_TOLERANCE_CENTS`); bowed notes currently land within ~0.5 cent (bundled songs ±0.1–0.2 ¢ mean), plucked/struck notes within ~4.5 cents. Re-measure after any synthesis change. Known traps: Tone.PluckSynth (Karplus–Strong) is 3–7 cents flat, so plucks are subtractive; a low-pass sweeping across the fundamental shifts pitch; worklet `AudioParam` `minValue`s must be 0, because Tone's `connectSignal` zeroes the intrinsic value and Chromium clamps it to `minValue` (a 20 Hz floor made every note 20 Hz sharp); too little force for the bow's speed or acceleration kicks the string into the octave regime; YIN's first dip is an octave high when the fundamental is weak, so `detectPitch` re-checks multiples of the period — and, the other way round, a noisy note (bow noise, flautando) dips lower at a multiple of its period, so a longer period is only accepted when the spectrum has energy between the shorter period's harmonics (`subharmonicDb`); Tone `normalRange` signals throw above 1, so the bow-speed signal is unit-less. Force must be *pressed* at once when the bow lands on a silent string (`applyTimbre(..., landing)`): easing it in while the bow already moves locks the heavy male string onto its octave (double slip) for the whole stroke, which pitch tests miss because the period survives — `bowed-string.test.ts` checks H2 < H1. Every re-bowed note after a released or stopped bow is a landing too (the worklet takes the string over as the bow speed comes up), including fast abrupt runs whose released bow is still moving; live strokes (scheduled for "now": keys, pads, MIDI) hold the landing bow off the string for 12 ms (`liveHold`), because their events reach the audio thread a render quantum late and an unrendered zero lets the bow catch the ringing string in double slip. Check octave behaviour with a census over every song × style × random start offsets (different noise states), not a single render. The pitch lock must time the whole waveform: the band-passed fundamental reads several cents flat of it during the attack, and locking on it made low notes start up to 15 cents sharp.
- **Tone.Draw** drops callbacks while the window is hidden: use it only for visuals, and fire must-happen events (song end, sequencer end) from transport callbacks.
- **Domain choices and their sources**: `SCREEN_DIRECTION` puts Tatakh (pull) to the RIGHT — the bow hand moving away from the instrument, as in the spec's technique table and teaching sources (the generated playground mockup labels it the other way). Tunings: Mongolian F3–B♭3, Inner Mongolian G3–C4, fifth tunings (E♭–B♭; the spec/plan folk C–G and F–C). Vibrato is taught on open strings too, so it is not a verification warning. Erkhii darakh (thumb) is accepted on either string: the spec puts it under the male string, while most sources describe the thumb on the thin female string (C on the B♭ string). Scale length 566 mm (Woodford's plan, Bat-Ochir's chart). Soundbox Q values and the hide-top modes are estimates; the first-position fingering accepts both documented hand frames.
- **Performance styles** (`core/performance/`): ornaments are added only for listening; verification and `measurePitch` always use the notes as written. Ornament pitches come from the song's own pitch set (pentatonic neighbours of a 2nd or minor 3rd) and never a semitone the melody does not step by — a chromatic scoop from B♮ into C in an F-major tune was a concrete "doesn't sound Mongolian" bug. Measured on the conservatory reference: lyrical vibrato 5.0 Hz, ±13.5 cents median, at half depth ~130 ms into the note, no in-phase loudness swell, on most stopped notes ≥ 0.6 s (`references/measurements.md`); the stage preset now matches those rows in the Playlist comparison. `as-written` is notation only: no automatic vibrato, ornaments or bow shaping (notated vibrato, accents, tremolo still play). The Studio lead ignores a song's tempo map (the accompaniment is at constant tempo).
- **Reference recordings** live in the git-ignored `references/` folder with `manifest.json` (licence, md5, what each shows); they are for analysis only, never bundled, and downloading more needs the user's permission. **Private songs** (copyrighted works the user may use personally, e.g. "Маамуу нааш ир", protected until 2064) live in the git-ignored `local-songs/` folder and are imported in the app; never move them into `songs/` or copy their melodies into tests (use `core/performance/stage-etude.fixture.ts`).
- **Cultural accuracy**: only use Mongolian technique names that appear in the spec (blank otherwise). Bundled songs are original etudes; don't add transcriptions of copyrighted works, and give any traditional transcription a verifiable `source`. The only public-domain notation source found so far is J. Van Oost, "Recueil de chansons mongoles", *Anthropos* 3 (1908) — check any transcription from it by eye against the scan. Recordings (even CC-licensed ones) are performers' versions: don't transcribe tunes from them.

## Packaging

`electron-builder.yml` ships only `out/**` — renderer libraries are devDependencies because Vite bundles them. Builds are unsigned, so Windows SmartScreen warns on first run. A strict production CSP is injected at build time by the `productionCsp` plugin in `electron.vite.config.ts` (it allows `blob:` for the worklet and Tone's clock worker); the dev server runs without CSP. `vite.web.config.ts` reuses the renderer config for `dev:web`. `src/shared/project.ts` holds the repository URL (empty until published; links are hidden while empty).
